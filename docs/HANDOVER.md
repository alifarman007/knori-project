# Handover package

The proposal makes two commitments about what Sway receives. Section 9
(*Source-Code Access*) says which categories of artefact are provided. Section 10
(*Portability*) lists what Sway receives **at every Phase acceptance**.

This document maps both lists to real files in this repository, and says plainly where
something is not there yet.

A status of **Ready** means the artefact exists and was checked. **Partial** means
some of it exists. **Outstanding** means it does not exist.

## How to get the missing items

Ordered by how much they block.

1. **Dockerfiles and the image build** (item 2). Two Dockerfiles — one for the Python
   image used by api, worker and migrate, one for the Next.js standalone build — and a
   CI job that pushes them to GHCR on `main`. Everything else in the deployment path
   is already written and waiting for them: `deploy.sh` pulls a tag, migrates, polls
   `/readyz` and rolls itself back if it never goes green.
2. **`docs/credentials.md`** (item 11). A table of every account, who owns it, what it
   costs, and the steps to transfer it. Nothing technical; it just has to be written
   down while the person who created the accounts still remembers.
3. **`docs/schema.sql`** (item 3). `./run db && ./run migrate && ./run schema`.
4. **Run the restore drill** (item 9). `deploy/scripts/restore.sh` does it and prints
   the timings. Write the total into the table in [RUNBOOK.md](RUNBOOK.md) §6 — that
   number, not the restore, is the deliverable.
5. **Walk `deploy/README.md`** (item 7) with an engineer who did not build this, on a
   throwaway server, and time it. That is the acceptance test for the documentation.
6. **Run the evals and keep the reports** (item 9). The largest remaining piece. The
   machinery and the persona corpus are in `backend/evals/`; what has not happened is
   a run, because a run costs money. Until one happens, nothing measures Recognition
   *quality* — see the gates in [TESTING.md](TESTING.md).

## What the receiving engineer should read, in order

Written for someone who has never seen this code.

1. **[README.md](../README.md)** — what it is, and how to run it locally. No API key
   needed; `LLM_MODE=fake` runs the whole product. Then `./run seed alex` for an
   account that already has history, memory and Recognitions in it.
2. **[ARCHITECTURE.md](ARCHITECTURE.md)** — the containers, one message end to end,
   the `ros`/`knori` split, the tables, the context builder, the event stream,
   security.
3. **[RECOGNITION.md](RECOGNITION.md)** — the engine. This is the part that is
   genuinely unusual, and the part worth an hour.
4. **`backend/ros/engine/pipeline.py`** — the whole loop in one file, in the order it
   happens.
5. **`backend/ros/engine/threshold.py`** and **`confidence.py`** — about 500 lines
   between them, pure functions, and the rules the product is built on.
6. **`config/thresholds.yaml`** — every constant those two use, with comments.
7. **[API.md](API.md)** and **[RUNBOOK.md](RUNBOOK.md)** when you need them.
8. **[PROGRESS.md](PROGRESS.md)** — what is not finished. Read it before planning
   anything.

Then run `./run test` and read `backend/tests/unit/test_threshold.py`. The rules are
easier to understand as a table of cases than as prose.

## The acceptance question

The proposal states the Phase 1 acceptance test as: *"Is this a real product we can put
in front of paying customers?"*, and adds that success also requires Recognition to be
**evidence-grounded, inspectable and correctable**.

Those three are answered one by one, with the code that does it, in
[ACCEPTANCE.md](ACCEPTANCE.md).
