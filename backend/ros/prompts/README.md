# Prompts

The words KnoRI actually uses. Everything the product says about a person is generated by
one of the files below, and the rules those files impose are half of the Recognition
policy (`ros/policy/recognition_policy.md` is the other half, and it is loaded into
`interpret.recognize` at run time).

## Layout

```
ros/prompts/<task with . replaced by />/v<N>.md
```

`chat.reply` → `chat/reply/v1.md`, `interpret.recognize` → `interpret/recognize/v1.md`.
This matches the call in plan §4.3: `llm.run("interpret.recognize", prompt="interpret/recognize", …)`.

## File format

```
---
name: interpret.recognize
version: 1
task: interpret.recognize
schema: InterpretationBatch
changelog: first version
---
<Jinja2 body>
```

- Exactly these five front-matter keys. `schema` is a class name in
  `ros/schemas/llm_io.py`, or `null` for a task that returns free text.
- The body is Jinja2 with `StrictUndefined`: **every variable in the table below must be
  passed on every call**, including the ones that are usually empty. Pass `""`, `None` or
  `[]` — never leave one out, or the render raises instead of silently producing a prompt
  with a hole in it.
- Every block tag is written `{%- … %}`, so the files render identically whether or not the
  Environment sets `trim_blocks` / `lstrip_blocks`. Keep that style in new versions.
- **Immutable once merged.** A change is `v2.md`, never an edit. `llm_calls` stores
  `prompt_name`, `prompt_version` and `prompt_hash`, so a decision taken last month can
  still be explained by the exact words that produced it. `config/model_routing.yaml` pins
  which version each task uses.

## Block markers (`chat.reply` only)

`chat/reply/v1.md` contains three sections separated by marker lines:

```
<!-- knori:block system_a -->   persona and rules      stable, cacheable
<!-- knori:block system_b -->   profile, cards, corrections   per user, changes rarely
<!-- knori:block turn_context --> retrieved context and today's date  volatile, never cached
```

The context builder splits the rendered text on these lines and places the parts as
described in plan §5.4: A and B become system blocks, `turn_context` is prepended to the
current user turn so the cached prefix stays free of timestamps. A loader that ignores the
markers still gets a valid, working prompt — one block instead of three, with worse cache
behaviour.

No other prompt uses markers.

## Tasks

| Task | Schema | Model (plan §6.2) | Variables |
|---|---|---|---|
| `chat.reply` | – (stream) | Opus | `profile_text` str · `open_recognitions` [title, label, state] · `assertions` [statement] · `retrieved_context` str · `user_name` · `chat_style` · `today` |
| `extract.signals` | `SignalExtraction` | Sonnet | `messages` [ref, sent_at, text] · `recent_context` [role, text] · `memory_context` [str] · `topics` [key, description] · `sensitive_categories` [key, description] |
| `interpret.recognize` | `InterpretationBatch` | Opus | `policy_text` str · `topics` · `assertions` [kind, statement] · `do_not_repropose` [str] · `open_interpretations` [ref, kind, topic, status, statement, evidence[ref, when, role, quote]] · `new_signals` [ref, when, topic, kind, strength, content, quote] · `neighborhood_signals` (same shape) · `today` |
| `recognize.compose` | `RecognitionDraft` | Opus | `statement` · `rationale` · `kind` · `confidence_label` · `support_count` · `distinct_days` · `evidence` [ref, when, quote] · `assertions` [kind, statement] · `user_name` · `chat_style` |
| `correction.parse` | `CorrectionParse` | Opus | `card_title` · `card_body` · `card_explanation` · `statement` · `evidence` [ref, when, quote] · `correction_text` · `topics` |
| `claims.same_claim` | `SameClaim` | Opus | `claim_a` · `claim_b` · `b_kind` (what B is, in words: "another claim KnoRI is tracking", "a correction they made", "a fact they told KnoRI") |
| `summarize.conversation` | `ConversationSummary` | Sonnet | `messages` [role, text] · `previous_summary` str or empty · `user_name` |
| `profile.compile` | `ProfileBuild` | Sonnet | `user_name` · `chat_style` · `memory_items` [kind, statement] · `accepted_recognitions` [title, statement] · `corrections` [kind, statement] · `do_not_notice` [str] · `today` |
| `chat.opener` | – | Sonnet | `user_name` · `chat_style` · `days_away` str · `last_summary` str or empty · `open_threads` [str] · `new_recognitions_count` int |
| `onboarding.parse` | `OnboardingParse` | Sonnet | `answers` [ref, question, answer] · `topics` · `sensitive_categories` |
| `chat.title` | `ChatTitle` | Sonnet | `messages` [role, text] |
| `eval.judge_match` | – (JSON in body) | Opus, offline | `gold` (statement, note) · `candidates` [ref, title, body] |
| `eval.judge_grounding` | – (JSON in body) | Opus, offline | `card_title` · `card_body` · `card_explanation` · `quotes` [ref, when, quote] |

`topics` and `sensitive_categories` are the lists in `ros/policy/topics.yaml`, loaded as
they are — each entry already has `key` and `description`, so no transformation is needed.

The two `eval.judge_*` prompts have no schema in `ros/schemas/llm_io.py`; the exact JSON
object they must return is written out in each file. The eval runner should define matching
Pydantic models in `backend/evals/` and validate the text itself.

## Conventions every prompt follows

- **Short ids, never UUIDs.** `S12` for a signal, `I3` for an interpretation, `R2` for a
  card, `M4` for a message, `A1` for an onboarding answer. A hallucinated id then matches
  nothing and the item is dropped rather than mis-attached.
- **Quotes are copied, never retyped.** Anything asking for `quote_text` says so at length,
  because an inexact quote fails the offset check at insert and the observation is lost.
- **Untrusted input is fenced and labelled.** Anything the user wrote sits inside a named
  tag (`<new_messages>`, `<their_correction>`, `<retrieved_context>`) and every prompt that
  contains one says explicitly that its contents are a record, not instructions.
- **Third person inside the engine, second person only on the card.** Signals,
  interpretations, assertions and the profile are all "They …". `recognize.compose` is the
  one place that turns a claim into "you".
- **Abstaining is allowed everywhere.** Every extraction, interpretation and parse prompt
  states what to return when the honest answer is nothing.

## Adding a version

1. Copy `vN.md` to `vN+1.md`, edit, and write one line of `changelog` saying what changed
   and why.
2. Point `config/model_routing.yaml` at the new version.
3. Run `make eval` on the affected personas before and after. A prompt change with no
   before/after numbers is a guess.
4. Leave the old file in place forever.
